## H01：把背景写入从模型生成中拆开

1. **发现问题**：用户照系统提示回复“确认保存全部”仍不保存，反而重新产生候选；另有部分确认及重复说明反馈。保存聊天也不能被当作已确认经历。（S06）
2. **根因分析**：初版前后端重复匹配确认语法，后台有限语法漏掉系统自己提示的原句；返回 CONFIRMATION_UNCLEAR 后进入普通模型请求。旧候选变化与用户确认之间也存在核对窗口。某次现场未抓包，不能认定所有重复提炼均同因。（S06）
3. **方案取舍**：采用后台唯一确认解析器、明确按钮和确切版本绑定。放弃依赖模型再次判断“用户确认了什么”的写入路径，确认只做数据库操作。取舍代价是有限语法覆盖，不承诺任意同义表达。（S06；“生成与写入分权”是基于机制的能力归纳）
4. **关键实现**：候选、确认、有效背景分表；绑定人物、工作区、候选版本、展示正文、上下文代次及实际确认项；部分确认仅保存对应项。重复键回放，保存失败原键重试，旧版本/旧代次拒绝。修复提示原句，发送前核对候选，显式“保存全部候选”不调用模型。（S06）
5. **验证方式**：模型替身生成两条候选，原句确认后有效表仅增加两条、候选消失；重复确认不重复落库，总模型计数仍为生成时的 1 次。数据库约束注入失败后回滚并原键重试；否定、假设、未展示/扩大内容不写入；浏览器 fixture 覆盖原句和503重试，不 POST conversation。（S06）
6. **结果/证据**：在已覆盖表达和故障用例中实现明确确认后落库、确认重试不再调用模型；用户后续确认 M06 无其他问题。**待补证据**：完整真实模型走读、确认表达样本集/误接收率；不能写“消除幻觉”或通用意图准确率。（S06/S09）

面试抓手：为什么“候选已展示”和“聊天里说确认”仍不够？为何必须绑定版本、正文与代次？幂等如何避免失败重试重复记录？

## H02：外部调用不可原子提交时的请求与结果恢复

1. **发现问题**：刷新、两页发送、提交响应丢失或重启可能诱发重复调用；模型返回后数据库写失败又可能让用户重新付费生成。外部执行和本地事务不能原子提交。（D04、S04）
2. **根因分析**：浏览器未收到响应不能证明后端未受理；CALLING 后缺结果不能证明供应商未执行；生成成功也不代表回答已保存。一个“成功/失败”状态不足以区分这些窗口。（D04、S04/S08）
3. **方案取舍**：选择持久请求+短事务+单线程执行，区分 execution_status 和 record_status；未知结果不自动重试，保留用户风险决定。当前不引入 MQ/跨实例租约。内存暂存可提供当前进程恢复，代价是崩溃窗口会丢正文。（S04/S08、C03/C05）
4. **关键实现**：受理校验归属、指纹/幂等、版本和同区状态；全局短 advisory lock 与工作区行锁控制默认4项受理上限；用户消息及输入快照同事务保存。FOR UPDATE SKIP LOCKED 领取 ACCEPTED 并提交 CALLING，事务外调用模型，短事务落结果；回答先入 unsaved 再持久化。启动持 WorkerGuard 后将遗留 CALLING 改 UNKNOWN；保存重试只用已有结果，轮询只查原请求。（C03/C05、S08）
5. **验证方式**：替身精确计数验证同键同请求、同区第二次拒绝和未知不重调；数据库 CHECK 故障注入证明回答可查询、发送受阻、解除故障仅重试保存且模型仍1次。独立随机 schema 的真实 JAR 构造 ACCEPTED/CALLING/SAVE_FAILED，强杀重启核验恢复、锁及丢失提示。第5项超限拒绝且保留草稿。（S04/S08）
6. **结果/证据**：已覆盖重放、落库失败和重启场景按执行阶段恢复，避免在这些路径自动重新调用模型。真实合成浏览器请求亦记录成功并刷新恢复。**边界**：不保证供应商端恰好一次，不保证崩溃后找回答案；多实例、精确崩溃窗口、真实DB故障组合仍待验证。（S04/S08/S09）

面试抓手：为什么进入 CALLING 但实际尚未外发也保守标未知？文件锁适用范围是什么？幂等、乐观版本和行锁分别解决什么？

## H03：修复“响应头已到、正文仍无限等待”

1. **发现问题**：用户反馈简单问题偶发数分钟等待且无法停止；清空未知结果后还会卡住无法发送。（S06）
2. **根因分析**：BodyHandlers.ofInputStream 在响应头到达后已完成请求，后续 readNBytes 不受原 request timeout 的完整正文期限保护。停止后若不校验结果落库状态，旧线程可能写入迟到结果。清空隐藏 UNKNOWN 后原门禁仍扫描全部未知请求，确认按钮却已消失。（S06）
3. **方案取舍**：对完整响应 future 施加期限；停止仅中断本地等待、释放门禁并放弃迟到结果，不承诺供应商取消；不自动重试/换模型。受理排队时间另计。（S06）
4. **关键实现**：Java HttpClient.sendAsync + pending.get 限时等待，失败取消 future、保留线程中断；连接15秒、完整响应60秒。后续增补接收中2 MiB上限。stop-waiting 短事务锁工作区转已确认风险 UNKNOWN；保存/失败更新必须仍为 CALLING。未知门禁仅检查可见请求，清空明确费用风险。（C03/C04、S06/S08）
5. **验证方式**：本地 HTTP 服务先发响应头和空格，再阻塞正文；测试期限800ms，断言3秒内退出、HTTP计数1。阻塞模型替身测试停止→允许新请求→旧结果迟到不落库；未知不确认→清空→新请求受理。浏览器 fixture 核验停止入口解除发送禁用。（S06、C07）
6. **结果/证据**：用可复现故障证明期限覆盖完整正文且不自动重调，已覆盖停止及隐藏未知请求门禁回归。**边界**：没有证明供应商延迟根因或取消收费；2 MiB超大响应尚缺专项测试记录，不能把该限额声称为已完成故障实测。（S06/S08）

面试抓手：请求 timeout、连接 timeout、响应体消费期限有何区别？future.cancel 如何与数据库状态保护配合？

## H04：资料会变，但在途回答的依据不能悄悄换

1. **发现问题**：材料停止参考、背景撤回或更新后，旧聊天可能仍含旧描述；在途请求与最新界面可能出现不同依据。资料总量增长也可能导致静默遗漏。（D02/D03、S04/S05/S07）
2. **根因分析**：历史消息、有效背景、当前材料不是同一数据域；异步请求若执行时再读最新内容会改变受理意图，仅更新界面也不能改变已发模型输入。（D04、S07）
3. **方案取舍**：受理固定输入，另存版本清单提示失效；下一次用最新背景和变更说明。在途不自动重跑；必需资料超预算拒绝，历史按完整问答选择。没有向量检索、相关性过滤或摘要，代价是容量和长期变更说明增长。（S05/S07、C03）
4. **关键实现**：后端从归属关系读取简历开关、选定材料及解析限制、同人全部有效背景；版本条件校验后保存 input_json/basis_json。basisChanged 比较背景/材料/简历版本。输入采用192 KiB UTF-8本地预算，近期完整成功问答按分隔点加入；epoch/version 阻止旧页复活清空的上下文；撤回说明不作为有效事实。（C03、S05/S07）
5. **验证方式**：截获替身输入断言未选材料不进入、取消简历有效、分隔前消息不发送。延迟请求中更新背景/材料，断言原快照未变、旧回答有变化提示、下一次实际输入包含最新背景及变更说明。容量用例整轮排除超长历史，必需资料超限不调用；两页清空后旧输入不自动写回。（S04/S05/S07）
6. **结果/证据**：在覆盖用例中实现可检查的当前范围、稳定在途快照和新旧依据提示。**边界**：不能承诺撤销外发数据、语义遗忘、模型始终遵循撤回说明或全面防提示注入；四类语义冲突真实走读待补。（S07/S09）

面试抓手：input_json 与 basis_json 为什么分开？停止参考为什么不等于删除旧消息？字节预算与 token 上限有何差别？

## H05：文件移动与数据库提交无法同事务

1. **发现问题**：上传建立简历时可能文本已入库、原件移动失败；只显示“保存成功”会误导，重新上传又可能重复建稿。清理时不能按文件年龄直接删除。（S02）
2. **根因分析**：本地文件系统与数据库不共享事务；解析文本可用性和原件就绪状态是不同维度。数据库引用不可读时无法证明文件无业务引用。（D04、S02/S08）
3. **方案取舍**：采用临时文件、明确文件状态、提交后原子移动及补偿重试；文本已保存仍可用，不强行伪装跨系统原子性。当前单机本地存储，未引入对象存储或分布式事务。（S02；“跨系统最终补偿”是机制归纳）
4. **关键实现**：随机存储键代替原始文件名拼路径；临时写→短事务保存文本/PENDING来源→正式化→READY。重试只恢复原件与状态，不新增修订；下载先校验归属。清理按引用清单，临时1小时、无引用正式文件1天，活动上传/有效引用保留，DB不可读停止删除。测试原件目录与正式目录分离。（S02/S08）
5. **验证方式**：暂移临时文件注入正式化失败，核验正文成功、PENDING；恢复后只重试文件且修订数仍为1；外事务回滚目标仍未建立。下载字节一致、编辑正文不改原件；临时目录构造过期孤儿/有效引用/活动上传，并注入引用查询失败核验不删。（S02/S08）
6. **结果/证据**：覆盖故障下文本与原件分别反馈、补偿不重复建稿、引用清理不误删被测有效文件。**边界**：未完成全部磁盘/真实DB故障、进程崩溃全窗口、备份恢复；解析无OCR、非恶意文件沙箱。（S02/S08）

面试抓手：文件已移动但READY更新失败如何重试？为什么数据库不可读必须停止清理？

## H06：防旧保存响应和发送检查误覆盖新输入

1. **发现问题**：多页保存可能覆盖新版本；M09回归发现发送前等待候选、草稿、简历检查时仍读取可变输入框，可能把下一条新文字当本次消息并清空。（S01/S05/S09）
2. **根因分析**：按钮防重不处理跨页并发；异步函数中的响应时间与用户持续编辑不同步。早期测试只验证新草稿保留，未核对实际POST正文，漏掉了发送内容错误。（S09）
3. **方案取舍**：服务端版本条件/工作区锁拒绝过期覆盖；客户端每次提交绑定文字快照，旧响应只确认原提交。冲突保留输入并核对，不做自动合并或实时协同。（S01/S05/S09）
4. **关键实现**：简历/草稿版本与上下文epoch校验，清空/保存采用一致工作区锁序；send起始固定 submitted，候选确认和普通模型POST使用同一快照；成功仅在当前输入等于submitted时清空，否则继续保存新草稿。（C06、S01/S05）
5. **验证方式**：两页保存只一方成功、另一方冲突并保稿；慢保存期间新编辑不被旧响应确认；两标签页清空后旧输入暂停回写。M09浏览器延迟发送前检查期间写下一条，追加POST正文必须等于点击发送时文字，并核验新草稿刷新恢复。（S01/S05/S09）
6. **结果/证据**：修复本次被复现的错误消息提交与新草稿误清风险，补上请求正文与页面状态双断言。**边界**：尚未穷尽全部跨页竞态；这是项目全栈可靠性成果，个人前端/后端贡献需分别确认。（S09）

面试抓手：为什么“输入框最后还在”不足以证明发送正确？幂等为何不能替代乐观版本？
