# “调用结果不明”的实际数据流程

本文按当前代码解释页面文案“调用结果不明，不会自动重调；重新调用可能重复收费。”的来源，便于 MVP 完成后回看学习。它是本应用依据请求状态生成的提示，**不是 DeepSeek 返回的一段 AI 回答**。

## 1. 从点击发送到请求受理

前端 `frontend/src/conversation.ts` 的 `send()`：先处理背景明确确认等本地业务分支；普通问题才向 `POST /api/v1/profiles/{p}/workspaces/{w}/conversation` 提交消息、资料版本、对话版本/代次及 `Idempotency-Key`。参考简历时先保存，失败不外发。

后台 `ConversationService.send()` 校验归属、版本、同区状态、全局上限和容量。短事务写入：

| 数据 | 作用 |
| --- | --- |
| `ai_request.message` | 本次用户问题 |
| `ai_request.input_json` | 受理时固定的模型输入，含允许资料与预算内历史，不含 API key |
| `ai_request.basis_json` | 资料版本清单，用于提示依据变化 |
| `execution_status=ACCEPTED` | 已受理，尚未进入外部调用阶段 |
| `record_status=PENDING` | 本次请求还未完成记录处理 |
| `conversation_message` 的 user 行 | 回看的用户消息，与 request_id 关联 |

接口正常返回 HTTP 202 与请求 ID。页面清除对应已提交文字，保留回答期间新写草稿。**受理成功不代表供应商已执行或生成成功。**提交响应丢失属于另一个“提交是否成功未知”的问题，不能直接认定是模型 UNKNOWN；应利用原键/原请求查询，不能盲目新键重发。

## 2. 后台领取与真实 HTTP 调用

单后台执行器 `ConversationService.tick()` 约每 500ms 轮询，原子选择 ACCEPTED 请求并在短事务中置为 CALLING。之后释放事务，再调用 `DeepSeekGateway.complete(input_json)`。只有领取和状态写入使用短事务，等待外部 HTTP 不持有数据库事务。

适配器向固定地址 `https://api.deepseek.com/chat/completions` POST JSON，密钥只放 Authorization 请求头。当前模型为 deepseek-flash，非流式，关闭思考。单次只发送一次；不跳转、不自动重试、不静默切换供应商。

连接超时 15 秒；从 HTTP 请求到完整响应体的总期限为 60 秒。期限不包含前面的队列等待、页面轮询间隔或数据库故障耗时，也不承诺 60 秒内一定获得成功回答。总期限到达会取消本地 future，但无法据此证明供应商未执行或未收费。

## 3. 为什么会判为 UNKNOWN

`ModelGateway.Failure` 用 `code` 和 `unknown` 布尔值区分已知失败与结果不明。当前分支如下：

| 来源 | 当前处理 |
| --- | --- |
| 超时、连接/传输异常、解析异常等 | MODEL_RESULT_UNKNOWN，unknown=true；保守表示缺少可可靠使用的结果，并非已确认供应商执行 |
| HTTP 5xx 或 408 | SUPPLIER_HTTP_xxx，unknown=true |
| 空白回答、响应超过本地大小限制 | MODEL_EMPTY_RESPONSE / MODEL_RESPONSE_TOO_LARGE，unknown=true |
| HTTP 400/401/402/429 等非上述状态 | MODEL_FAILED，保留安全错误码，不直接归类 UNKNOWN；其中 402 是余额不足 |
| 进程启动时遗留 CALLING | 取得本项目执行器锁后标 UNKNOWN，不自动重新执行 |
| 用户主动停止等待 | 置 UNKNOWN 且 UNKNOWN_ACKNOWLEDGED，尝试中断本地 HTTP；明确放弃迟到结果 |

进入 CALLING 只代表系统已到“可能外发”的阶段，崩溃也可能发生在实际 HTTP 之前。系统宁可保守标未知，也不以自动重试冒重复费用风险。UNKNOWN 不等于“没有余额”、不等于“供应商肯定失败”、也不等于“回答已生成但保存失败”。

## 4. UNKNOWN 如何落库

适配器抛出 unknown=true 的 Failure 后，`ConversationService.tick()` 条件更新原 request_id：

```text
execution_status = UNKNOWN
record_status    = SAVED
error_code       = MODEL_RESULT_UNKNOWN 或安全供应商状态码
input_json       = 空字符串
updated_at       = 当前时间
```

更新要求原状态仍为 CALLING，避免停止等待后旧执行器覆盖新状态。用户问题保留，`answer` 没有可用正文，也不会添加 assistant 消息或背景。这里 **SAVED 表示“未知结果这一状态已记录”，不表示模型回答已保存**。

如果这一步数据库也不可用，页面暂时可能仍看到 CALLING，不能声称状态一定即时变 UNKNOWN。旧状态恢复和进程故障组合仍需 M08 验证。

## 5. 从数据库到用户看到的提示

前端 `poll()` 每轮结束后约 1.5 秒再查询会话；对 ACCEPTED/CALLING 或 SAVE_FAILED 的请求另查原请求接口。`get()` / `conversation()` 返回 execution_status、record_status、error_code、answer 等字段，不返回执行快照或 key。

页面检查 `task.execution_status==='UNKNOWN'`，直接渲染固定文案：

> 调用结果不明，不会自动重调；重新调用可能重复收费。

因此这段话不是模型生成，不消耗一轮额外 tokens。轮询只查询状态，也不会重新调用模型。查询网络异常使用“暂时无法获取状态”提示，不能把查询失败直接改成模型失败。

## 6. 用户下一步与数据变化

- **确认风险，允许下一次发送**：POST 原请求的 `/acknowledge-unknown`，后台将 error_code 改为 UNKNOWN_ACKNOWLEDGED。原状态仍是 UNKNOWN，不伪造回答。只解除可见未知请求的发送门禁，不自动发送；下一次主动发送创建新请求，可能产生新的费用。
- **停止等待**：在途请求经 `/stop-waiting` 转为已确认风险的 UNKNOWN，释放区内占用并尝试中断本地线程。旧 HTTP 返回后状态不再是 CALLING，不写回答、不创建背景、不覆盖新请求。供应商端是否停止无法保证。
- **清空记录**：无活动请求/未保存回答阻塞时，删除本区可回看消息、清草稿、隐藏请求并清正文，增加上下文代次。发送门禁只检查可见 UNKNOWN，避免清空隐藏按钮后无法解锁。提示已说明旧调用可能收费，不承诺撤回外发内容。
- **刷新/重开**：查询原请求已保存状态，不自动重新调用。没有额外后台“免费补答”逻辑。

## 7. 与“回答保存失败”的区别

成功获得回答后，先在进程内 `unsaved` 暂存，再短事务写 assistant 消息、供应商标识、用量及候选。成功后 SUCCEEDED/SAVED，清输入快照。落库失败时 SAVE_FAILED，页面可看到暂存回答，提供“重试保存回答”，只重试数据库，不重调模型；进程重启可能丢失内存结果，不能保证恢复。这个分支不应与缺少可靠结果的 UNKNOWN 混同。

## 8. 已有证据与边界

- 本地 HTTP 替身发送响应头和空格后阻塞正文，800ms 测试期限内结束等待，3 秒内退出，HTTP 计数为 1。证明总期限覆盖完整正文，不是供应商延迟实测。
- 模型替身验证未知结果不自动重调、风险确认后主动新发、清空未知结果后可发送，以及停止后迟到结果不落库。
- 真实供应商是否执行/收费以其账单与可查询能力为准。本应用不能靠 UNKNOWN 推算费用，也不能承诺端到端恰好执行一次。
