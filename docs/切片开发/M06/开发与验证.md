# M06 开发与验证

## “确认保存全部”重复询问修复

用户再次实测发现系统提示“确认保存全部”，回复原句却不保存。根因已复现：后台有限语法漏掉系统自己推荐的这句原话，返回 CONFIRMATION_UNCLEAR 后页面继续走普通模型请求，于是重新产生候选。此前自然确认测试覆盖了其他表达，但没有覆盖提示原句，属于实现与测试遗漏。

已新增“确认保存全部”“确认全部保存”“确认全部并保存”等全量确认表达，仍全句匹配，否定/假设/附加修改不会误保存。页面新增“保存全部候选”明确操作，绑定当前已展示的候选版本、正文，直接调用确认接口，不调用模型；旧候选状态仍由后台拒绝。

新增后台集成用例：从模型替身产生两项候选，原句确认后有效表出现两项、待确认候选消失、重复确认不重复落库、模型总调用仍只有生成候选的一次。浏览器用例改用用户原话，验证失败原键重试后两项在背景列表显示且未 POST conversation。

执行过程的两次失败揭示运行中的旧版正式执行器会与开发库中的测试请求竞争，出现测试暂存回答缺失/候选缺失。没有停止用户进程；后端 verify 与 browser smoke 已改用专属 m00_test schema，正式运行仍使用 m00_app。新执行器还只领取自身模型标识任务。隔离后基础 schema 用例相应更新，最终构建与 40 项测试通过。先前竞争可能让旧执行器接收合成测试任务，不能再声称这两次失败运行绝无外发；本次未主动触发真实模型测试，后续验证隔离防止重现。

模型与消费疑问的代码、官方文档及只读余额核查见 [模型与计费核查](模型与计费核查.md)。当前 flash 为官方真实模型，查询时余额可用；不将测试替身数据当作真实账单。

## 用户四项反馈修复（2026-11-24）

用户实测发现：候选与确认说明冗余，明确回复仍反复提炼；简单问题偶发数分钟等待；无法停止；未确认未知费用风险就清空后无法发送。本节为最新修复状态，下面初版有限语句与未提供停止入口的描述仅保留为过程记录。

1. **确认与重复展示。**初版前后端分别匹配确认语法，中文编号、“仅保留”“确认并保存”等不被覆盖；模型 answer 又重复输出系统追加的候选。本次删除前端确认正则分流，由后台唯一解析器处理已展示候选，新增“仅保留第一项作为背景”“确认仅保留第一项”“确认”“确认保存”“确认并保存”等明确表达，仍拒绝夹带修改、否定、假设和未展示内容。发送前刷新候选；候选发生变化先核对，不能把用户对旧内容的确认应用到新版本。候选答案只渲染一次确切编号清单和简短用途，提示模型不要重复规则。原始反馈中最后一句未进入保存的具体运行现场未留抓包，不能断言仅由正则造成；本次同时消除前后端分流和轮询时间窗。
2. **长时间等待。**确定的代码缺陷是 `BodyHandlers.ofInputStream()` 在响应头后就完成请求，后续 `readNBytes()` 不受原 request timeout 的完整响应期限保护。改为异步接收完整响应体，并对整个 future 设置 60 秒期限，超时/中断取消本地 future，不自动重试。连接超时仍为 15 秒。供应商或网络为何偶发延迟不能仅凭本地代码定论；这次解决客户端无限等待边界，不宣称修好了供应商服务质量。单执行器仍可能有最多 4 个受理请求的排队时间。
3. **停止等待。**新增受保护的 POST `/api/v1/profiles/{p}/workspaces/{w}/requests/{r}/stop-waiting`，必须主动确认供应商可能仍执行并收费。短事务锁工作区，将活动请求转为已确认风险的 UNKNOWN，释放本区发送门禁，再尝试中断本地线程与 HTTP future。未外发的 ACCEPTED 请求也可释放；不谎称供应商已经取消。结果保存/失败写入都要求仍处于 CALLING，旧结果不得新增背景、回答或覆盖新状态；状态变化不是 SAVE_FAILED。此入口按当前状态幂等，不重新执行模型。
4. **清空后卡死。**原发送门禁扫描全部 UNKNOWN，而清空只隐藏请求，风险确认按钮随消息消失。门禁改为仅检查可见 UNKNOWN；清空确认同时明确旧调用可能计费且允许新问题，不再要求对已删除消息再次确认。已发生的隐藏 UNKNOWN 无需手工迁库，更新代码即可恢复发送。

此轮由用户明确授权增加停止等待，是对阶段设计原“无取消入口”的修订：只停止本地等待并放弃本次迟到结果，不承诺撤回供应商请求。未默认新增自动重试、供应商切换或流式输出。

验证：前端类型检查/构建和 39 项后端测试通过，0 失败/跳过。新增自然确认回归、重复候选展示断言、未知请求不确认→清空→新请求受理、阻塞替身→停止→新请求→旧结果迟到不写入。新增本地 HTTP 服务器先发送响应头与空格后阻塞正文，以缩短测试期限 800ms 复现并证明完整响应超时生效（3 秒内退出，只有一次 HTTP 请求）；未用真实模型制造等待。

M06 Chromium fixture 复测通过，覆盖用户原话“仅保留第一项作为背景”、503 后原键重试、不进入模型发送接口、停止等待按钮解除发送禁用。页面 fixture 与后端数据库/HTTP 替身测试分开计证，不称真实付费调用。本轮未读取输出密钥、未重新发起真实模型请求，未删除用户已有记录。

状态：进行中，基础实现与替身验证通过，待真实模型走读及用户页面体验。依据阶段设计 03 第 5 节、04 第 4.6 节及 05 第 9 节。M05 页面体验已由用户确认无异常并授权推进；前片未完成的运行恢复组合证据继续保留。

## 实现与契约

V8 新增 `background_candidate`、`background_confirmation`、`background`，独立保存候选、实际确认动作、有效背景。候选绑定人物、工作区、来源请求、版本、上下文代次和实际展示正文；每项编号从 1 开始。模型不能写有效背景。

模型输出采用 DeepSeek JSON Output：`{"answer":"普通回答","background_candidates":["确切经历"]}`，后台生成带用途的普通消息。官方文档 https://api-docs.deepseek.com/guides/json_mode 已核对支持 deepseek-flash、response_format=json_object，prompt 提供 JSON 示例。空结果/截断仍可能发生，不自动收费重试；非法候选结构不进入确认表。最多 8 项，每项 1000 字，不要求卡片或背景表。

| 接口 | 请求与结果 |
| --- | --- |
| GET `/api/v1/profiles/{p}/backgrounds` | 实际有效记录列表 |
| GET `/api/v1/profiles/{p}/workspaces/{w}/background-candidates` | 当前可确认候选，含 id/version/display_text/items；无候选为空对象 |
| POST `/api/v1/profiles/{p}/background-candidates/{c}/confirm` | Idempotency-Key；workspace_id、expected_version、displayed_text、user_text；返回实际保存项 |

确认在后台严格匹配明确表达，如“确认以上全部并保存”“以上完全准确，同意保存”“只确认第 1 项并保存”。允许指定多项编号；部分确认后其余项不自动保存。含糊、假设、否定、修正或附加未展示内容不匹配确认，按普通对话继续；模型如提出修正版，必须再次展示并确认。当前不是通用自然语言意图识别，不承诺任意同义表达都能保存。

确认记录保存原用户文字、确切候选版本及选择编号。重复操作只返回原结果，不重复新增；新对话提交使旧未确认候选失效，上下文代次变化也拒绝旧确认。背景数据库写失败事务回滚，页面保留确认与原幂等键，直接重试无需模型。继续对话可能使旧候选失效，届时先核对，不复活旧意图。

全部有效背景作为必需资料提供给同人物各区，纳入本地容量限制，其他人物不混入；清空本区对话不删除已确认背景。背景查看进入中间正文，右侧消息与草稿保持，返回简历不清空交流。

## 限制与后续

本轮未发起付费真实调用，尚缺设计要求的“协助部署”真实模型提炼→自然语言确认→列表端到端走读。用户可按页面体验步骤验证；未获得证据前不标整片完成。模型 JSON 不符合协议时保留普通回答但不创建可写候选，不自动重新调用。

任意语义确认、背景纠正/撤回、冲突澄清和背景在途版本变化属于尚待完成边界；后三项为 M07 范围，不提前宣称已交付。当前确认前要求来源回答可靠保存；回答暂存状态不能形成可确认候选，避免确认与展示版本脱节。进程重启/全部跨页竞态仍需后续组合验证。

技术认识：候选和有效背景必须分开，确认是用户对某一确切版本的独立数据库操作。这样重复提交和数据库失败可以安全重试，而无需让模型再次“猜测”用户确认了什么；代价是当前确认语句采用明确的有限语法。
