## 最新观察与交付决定

用户反馈切换HTTP/1.1后连续约8—9次回答未再出现原问题，目前情况比较稳定，明确同意MVP先按现状处理，后续再设计更完整兜底。本轮按“保留已知限制的试用交付，API风险暂时接受”记录，不继续要求人为复现或付费重放；下文阻断描述为当时排查状态，现不再将该偶发问题作为用户本轮试用交付的阻断。

这属于用户实际观察，不是受控协议A/B或稳定性保证，不证明HTTP2就是根因，也不证明供应商、网络或客户端未来不会波动。已有诊断、停止等待、保留输入、不自动重调、风险确认继续发送等机制继续有效；若再次发生，关联原请求阶段元数据回溯本文件和M04/M08。没有将未知调用自动切供应商或重试作为已实现兜底。

后续兜底候选：更清楚的等待进度和阶段反馈、失败后的原问题恢复与显式新尝试、保持草稿和已生成成果、网络/协议健康观测、经授权的供应商选择及费用提示。先设计后实施，尤其UNKNOWN不能盲目自动重调，避免重复收费及未经确认改变资料接收方。兜底降低影响，不保证外部服务永不失败。自动成稿、模板/PDF及成本收益尚未证明等产品边界仍保留，不因API观察改善宣称最初全部价值目标已达成。

按阶段设计01第2/3/7节复核，而非以切片数量判断完成。M00—M09含工程基础共10个编号，业务及验收片M01—M09为9片；进入最终片不代表全部完成。

## API现有证据与缺口

已有故障分为JSON模式空白回答、60/180秒完整响应超时及独立JVM崩溃，不能混为供应商故障。移除强制JSON后空白协议解析又出现混合正文问题，已修复；C2崩溃仅临时规避。此前延长期限未解决连续对话卡住，不能再记为根因修复。

旧超时请求没有响应阶段数据，无法事后恢复响应头/首字节，不猜测是网络或服务端排队。官方非流式接口可用空行保活，但只有观测到空行才可说本次符合该现象；收到HTTP200也不能证明模型已开始推理。

## 本轮诊断增量

V10新增ai_request.diagnostics_json；适配器在每次请求独立记录安全计时与计数，成功/失败均保存：elapsed_ms、headers_ms、http_status、http_version、first_byte_ms、first_content_ms、last_byte_ms、bytes_received、whitespace_bytes。stage区分WAITING_HEADERS、WAITING_BODY、KEEPALIVE_ONLY、BODY_RECEIVING。字段不含请求/回答正文、原始headers、URL或key，失败不自动重试，不额外生成调用。

超时判读：

- WAITING_HEADERS：未取得响应头，仍可能连接/TLS/服务端入口等待，不能单字段精确拆分；15秒连接超时不等于HTTP总耗时。
- WAITING_BODY：收到响应头但未有字节；结合HTTP状态排查。
- KEEPALIVE_ONLY：收到的字节全为空白，符合非流式服务端保活等待，但不证明内部排队原因。
- BODY_RECEIVING：收到非空白正文但未结束，可能传输中断或慢生成，需要结合最后接收时刻；不记录正文定位内容。

本地HTTP验证区分无响应头、空行保活、非空白半截正文，以及正常慢正文和完整响应；并验证安全字段不泄露key。普通请求仍180秒总期限，未改协议版本/连接复用策略，避免无证据修改多个变量。连接复用影响目前只是待验证假设，不是已发现原因。

本轮构建与59项后端测试通过（0失败/跳过），包括诊断字段落库、UNKNOWN不重调、清执行快照；文档及空白检查通过。测试迁移在m00_test应用V10，正式m00_app需用户保存后重启应用才迁移并启用新诊断；旧进程不会因重新构建自动更新。历史diagnostics为空不等于没有外发。
