# AgentCV 技术方案（第一版）

> 本文把 01—03 中已确认的产品与交互规则转换为可开发、可验证的技术约束。本文是第一版方案，不代表所有机制已经实现或实测通过。具体参数、模型服务能力和部署方式以开发验证结果为准；现有实现与目标方案明确区分。

## 1. 技术方案原则

AgentCV 不以堆叠组件展示技术复杂度，而以业务正确性为重点：资料不能串用，用户输入不能静默丢失，重复请求不能无意重做，旧内容不能覆盖新内容，失败状态不能冒充成功。

每个重要技术决策按以下方式演进：

1. 先写清业务约束和用户可感知结果。
2. 比较简单方案与更复杂方案，选择当前规模足够的方案。
3. 用并发、失败、重启和权限测试验证行为。
4. 记录方案代价、已知边界和重新评估条件。

本文的“采用”表示目标技术方向；不把文档中的目标接口或表结构误报为当前代码已经提供。

## 2. 技术栈与选型判断

### 2.1 当前基础

| 层次 | 采用技术 | 当前认识与适用范围 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite | 适合三栏工作台和局部状态交互；重点处理编辑、草稿、请求归属和切换状态 |
| 后端 | Java 17、Spring Boot 3.5、Spring Web | 适合单体 Web 应用、依赖注入、HTTP 接口和后台任务；不因此拆成微服务 |
| 数据访问 | Spring JDBC | SQL、事务和条件更新透明，适合学习并发与约束；代价是映射和查询代码需要自行维护 |
| 数据库 | PostgreSQL 17 | 提供外键、复合约束、事务、索引和条件更新，承担业务状态与文本数据 |
| 数据库迁移 | Flyway | 版本化演进表结构；迁移脚本只向前，不依赖手工改生产库 |
| 文件解析 | Apache POI、PDFBox | 支持 DOCX 和文本层 PDF；不承诺 OCR、排版还原或全部内容无遗漏 |
| 原件存储 | 本地文件目录（存储适配边界） | 适合单机/受保护局域环境；数据库保存元数据和提取文本，未来可替换对象存储 |
| 登录与安全 | Spring Security、服务端 Session、BCrypt | 适合当前单操作者同源应用；保留 HttpOnly、SameSite、CSRF 和登录限流保护 |
| 模型调用 | 后端统一适配器，MVP 一个服务商 | 密钥不进浏览器；业务模块决定权限，适配器只负责供应商协议与错误转换 |

### 2.2 暂不引入的基础设施

MVP 不提前引入 Redis、消息队列、向量数据库、微服务、Agent 编排框架或多供应商管理页面。数据库任务记录加有界后台执行器足以支持当前单操作者和轻量对话。

这不是永久禁止。出现多实例部署、任务量持续超过单体处理能力、需要跨进程队列或检索规模明显增长时，再通过实测比较引入新组件的收益和运维代价。

### 2.3 主要代价

- JDBC 控制力强，但需要自行保证参数绑定、映射、事务边界和错误处理。
- 本地文件和数据库不属于同一个事务，需要临时文件、状态字段和补偿清理。
- 外部模型调用不能与数据库提交组成原子事务，可能出现调用结果不明，不能承诺供应商端恰好执行一次。
- 服务端 Session 简化当前部署，但多实例或跨域客户端出现后需要重新评估会话存储和认证方案。

## 3. 部署与模块化单体架构

### 3.1 部署形态

```text
浏览器
  ├─ Vue/TypeScript 前端（开发时由 Vite 提供）
  └─ 生产时访问 Spring Boot 提供的静态资源和 /api/v1
          ├─ PostgreSQL 17：业务数据、文本、状态
          ├─ 本地文件目录：上传原件和来源文件
          └─ 一个模型服务商：由后端适配器调用
```

后端监听和数据库访问遵循当前受保护的本机/局域环境约束，不开放公网。前端不能直接携带模型密钥调用供应商。

### 3.2 业务模块

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 档案与工作区 | 人物归属、工作区创建、名称/方向和导航信息 | 模型调用、跨人物查询 |
| 工作区简历 | 导入预览、复制、独立保存、来源信息和版本冲突 | 自动修改材料或背景 |
| 个人材料 | 文件解析、文本、原件元数据、重命名和参考关系 | 将材料自动升级为背景 |
| 已确认背景 | 候选、确认、纠正、撤回、人物范围和版本 | 自行从模型回答中静默保存 |
| 对话与请求 | 消息、草稿、上下文分隔、请求受理、快照和结果 | 直接实现供应商协议 |
| 模型适配 | 请求转换、超时、供应商错误、返回值转换 | 判断用户是否有权使用资料或保存背景 |
| 文件存储 | 临时文件、正式文件、打开/下载和清理 | 决定业务归属和可见范围 |

模块先是代码依赖边界，不拆成多个 Maven 工程或网络服务。控制器只处理 HTTP 输入输出，业务服务负责规则，仓储/SQL 负责持久化，模型和文件访问通过适配接口隔离。

### 3.3 关键调用边界

1. 对话模块先验证人物、工作区、材料参考关系和背景状态。
2. 短事务固定本次请求依据、写入用户消息和请求记录。
3. 事务提交后调用模型，不在外部调用期间长期占用数据库事务或连接。
4. 模型返回后以短事务保存回答、状态和必要的依据元数据。
5. 模型不能直接写数据库；背景只有在用户确认并经过后端校验后才能保存。

## 4. 数据模型

### 4.1 六类业务对象

| 对象 | 归属 | 作用 |
| --- | --- | --- |
| `profile` 个人档案 | 操作者 | 表示哪一个人的资料，隔离人物数据 |
| `workspace` 工作区 | 一个 profile | 表示一个求职目标，名称和方向仅作辨识与标签 |
| `workspace_resume` 工作区简历 | 一个 workspace | 保存该区独立可编辑的简历和来源信息 |
| `material` 个人材料 | 一个 profile | 保存参考文本、解析状态、原件元数据；可被同人多个工作区引用 |
| `background` 已确认背景 | 一个 profile | 保存用户明确确认的具体经历，独立于材料和简历 |
| `conversation` 对话与请求 | 一个 workspace | 保存公开消息、输入草稿、上下文分隔和后台模型请求 |

实际落库可拆为版本表、关联表和状态表，但不能因拆表改变以上业务归属。

目标逻辑表如下，名称为设计名，按目标职责实现，不要求映射旧表或保留旧接口。符合设计且验证合格的旧代码可以复用。公共时间使用 `timestamptz`，标识使用 UUID，正文使用 text；版本为单调递增整数，数值在条件更新成功后递增。

| 逻辑表 | 关键字段与约束 |
| --- | --- |
| `profile` | `id, display_name, created_at`；名称不设唯一，允许同名 |
| `workspace` | `id, profile_id, name, direction, row_version, created_at`；保留 `(id, profile_id)` 唯一键供归属外键引用 |
| `resume_revision/current_resume` | `(workspace_id, revision)` 版本记录，`text, created_at, reason`；当前指针每区唯一，更新要求旧 revision 匹配；内部版本不等于提供历史稿恢复界面 |
| `resume_origin` | 每区一条建立来源，`kind, source_workspace_id, source_revision, file_id` 按来源类型选择；建立来源不随自动保存改写 |
| `stored_file` | `id, storage_key, original_name, media_type, byte_size, hash, file_status, created_at`；存储键唯一，不保存客户端绝对路径 |
| `material/material_text_revision` | 人物归属、展示名、正文版本、解析状态/限制、原件关联；重命名不递增正文版本或正文更新时间 |
| `workspace_material_reference` | 工作区、人物、材料的复合外键；`(workspace_id, material_id)` 唯一 |
| `background_candidate` | `id, profile_id, text, purpose, candidate_version, status, target_background_id, expected_target_version, source_message_id`；候选确认状态与有效背景独立 |
| `background/background_confirmation` | 背景文本、有效/撤回状态、版本；确认记录关联候选版本、实际确认部分和用户消息/交互动作，不接受任意模型声明代替确认 |
| `conversation_state` | 每区唯一，`conversation_version, context_epoch, boundary_sequence, scope_version`；控制清空、分隔和范围并发变化 |
| `conversation_message` | `id, workspace_id, sequence, role, text, request_id, created_at`；区内序号唯一，每次调用的用户/回答关联防重复 |
| `conversation_draft` | 每区唯一，`text, row_version, updated_at`；清空已发送草稿要求版本/内容匹配，不能删除回答期间新输入 |
| `ai_request/request_input` | `id, workspace_id, user_message_id, attempt, execution_status, record_status, claim_token, lease_until, model_config, supplier_request_id`；快照独立保存，包含资料版本清单和实际上下文边界 |
| `operation` | `scope, request_key, payload_hash, status, result_reference, created_at`；作用域加键唯一，重放前仍检查访问权限 |

领取令牌用于防止已失去租约的旧执行器继续外发或提交结果，状态推进必须同时匹配令牌和预期状态。请求结果索引按工作区和创建时间建立，材料名称搜索、排序索引及消息分页查询通过执行计划验证；不对所有字段盲目建索引。

### 4.2 必要关系与约束

- 所有对象通过服务端校验 `profile_id` 归属；不能只凭客户端提交的 UUID 访问数据。
- 工作区简历、对话和草稿不能跨工作区复用；人物背景只能在同一人物的工作区使用。
- 材料与工作区采用关联表，多区引用同一材料，不复制材料正文。
- 参考关系默认不建立，只有用户明确选择后才生效；停止参考不删除材料或旧消息。
- 简历、材料文本、背景和对话分别保存，更新一类对象不隐式改写其他对象。
- 重要对象使用 `row_version` 或等价版本字段；保存时带客户端已知版本，过期更新返回冲突而不是覆盖。
- 对外部写操作使用幂等键记录请求指纹和结果；相同键不同内容必须拒绝。
- 外键、检查约束和唯一约束承担最后一道数据边界，不能只依赖 Java 代码判断。

### 4.3 工作区简历版本

简历保存采用“版本记录＋当前指针”或等价结构：

- 当前版本保存可编辑文本、来源类型、来源标识和创建时间。
- 导入和复制建立独立简历；复制不复制对话、材料引用或其他工作区简历的后续变化。
- 上传成功建立简历后，来源文件记录在该工作区来源信息中，不进入个人材料库或 AI 参考范围。
- 保存条件包含工作区和预期版本。版本不匹配时返回 `VERSION_CONFLICT`，保留客户端文本和服务端最新版本供核对。
- 未完成导入预览不作为持久化简历草稿；离开后不承诺恢复。

### 4.4 材料和文件状态

材料正文和解析元数据进入数据库，原件通过不可猜测的存储键保存。至少区分：

`PENDING_FILE`、`TEXT_READY`、`PARTIAL_TEXT`、`FILE_MISSING`、`PARSE_FAILED`、`DELETED`（如未来支持删除）。

上述标识描述不同维度，落库拆成 `parse_status`（完整/部分/失败）、`file_status`（待就绪/就绪/缺失/不适用）和独立业务生命周期字段，不能用单个枚举让文件丢失覆盖解析结果。删除尚未纳入本轮能力，不因此增加删除入口。状态只在实际操作成功后更新。原件丢失但文本可读时，文本仍可参考，同时明确原件不可用；解析失败不能进入可参考范围。

### 4.5 对话、草稿和请求

- 每个工作区 MVP 只有一段可回看的对话和一份未发送草稿。
- 消息记录保存用户消息和 AI 公开回答；不保存隐藏思维链，不把消息记录等同于每次调用发送的完整历史。
- 请求记录保存受理状态、幂等键、工作区、消息关联、上下文分隔、依据版本、模型配置快照和供应商请求标识。
- 延迟执行使用必要的执行快照或不可变依据版本，确保受理时确定的资料不会被后续更新悄悄替换。
- 快照不包含模型密钥，且与长期聊天记录分开设置访问和清理策略。

### 4.6 背景候选与有效背景

候选表与有效背景表分开：

- 候选包含展示给用户的确切文本、保存用途、来源请求和候选版本。
- 用户确认关联候选版本和明确确认动作；确认部分内容只保存部分内容。
- 后端检查候选仍属于当前人物、版本未变化、确认目标明确且未重复处理后，才写入有效背景。
- 纠正生成新候选或新版本，不用旧确认覆盖新意图；撤回改变有效状态，不篡改旧聊天。

## 5. AI 请求执行与状态

### 5.1 受理流程

```text
发送消息
  -> 校验登录、归属、范围、容量和同区运行状态
  -> 短事务写入用户消息、幂等记录、请求和依据快照
  -> 返回 request_id
  -> 有界执行器领取请求
  -> 模型适配器调用供应商
  -> 短事务保存回答或失败状态
  -> 前端按 request_id 查询
```

受理时固定：工作区简历版本、选定材料及文本版本、全部有效背景版本、上下文分隔点和本次用户消息、模型服务配置。后续修改只影响下一次请求；在途回答按交互规则提示可能使用变更前依据。

### 5.2 状态与恢复

执行状态为 `ACCEPTED -> CLAIMED -> CALLING -> SUCCEEDED / MODEL_FAILED / UNKNOWN`。`CLAIMED` 仅在确认尚未进入外部调用阶段时允许租约到期后重新领取；必须先提交 `CALLING` 再尝试 HTTP 外发，遗留 `CALLING` 不自动重调，即使这会保守地把尚未实际外发的请求标成结果不明。领取使用数据库条件更新或短事务行锁，不把数据库锁带入外部调用。

对话保存状态另设 `PENDING / SAVED / SAVE_FAILED`，不与执行状态混用：模型已经生成不等于消息已经保存。MVP 不启用取消状态或取消入口。状态转换必须由服务端控制，不能由前端直接指定最终状态。

每区至多一条活动请求由数据库部分唯一约束或工作区行锁下的原子检查兜底，不能只依赖 JVM 锁。结果不明时需先查询并由用户明确决定是否承担重复费用发起新尝试；不能永久锁区，也不能自动认定外部调用已经结束。记录保存失败在解决前继续阻塞新发送。

| 情况 | 处理 |
| --- | --- |
| 已受理但未开始外部调用 | 可由后台执行器恢复 |
| 已可能发给供应商但无可靠结果 | 标记 `UNKNOWN`，不自动重调 |
| 回答已生成但聊天保存失败 | 回答可见，单独重试保存，不重调模型 |
| 模型明确失败 | 保留用户消息，允许用户手动重试；是否产生新调用必须明确 |
| 浏览器离开或刷新 | 不创建新请求，返回原请求状态 |
| 同区已有未结束请求 | 拒绝第二次受理或返回已有请求，不排队 |

回答先保留在后台结果暂存区，页面查询可看到回答及独立保存状态，随后写入公开聊天记录；保存重试只使用该结果。若数据库不可用，暂存可在当前进程内存中保留，但必须明确其不是可靠持久化：重启后可能丢失，浏览器应保留已显示文字并提供复制。上线前通过故障注入验证该路径；不能只在数据库保存成功后才向页面暴露回答，否则无法满足“回答生成但记录保存失败仍可见”。

后台执行器有界，并设置全局受理和运行上限。具体数值在压测和本机资源验证后确定，不把暂定参数写成容量承诺。

### 5.3 容量处理

- 系统规则、本次问题、本次勾选的工作区简历、选定材料和全部有效背景是必需范围；放不下时暂停受理，提示用户调整范围或内容，不静默删减。预算预留回答空间，本地估算不等于供应商一定接受。
- 历史聊天按上下文分隔点和容量携带近期完整交流，不截断半句话；较早消息可能不参与本次回答时明确告知。
- MVP 不自动生成摘要替代较早聊天，也不在发现供应商拒绝后自动缩减资料重新收费调用。

## 6. 文件与数据库一致性

上传使用临时文件和明确状态：

1. 接收文件并写入临时目录，校验大小、类型和路径安全。
2. 解析文本并反馈完整、部分提取或失败状态。
3. 数据库短事务保存对象归属、文本、哈希和待就绪状态。
4. 临时文件原子移动为正式存储键，成功后更新文件就绪状态。
5. 任一步骤失败都不显示整体成功；后台清理孤儿临时文件和无引用正式文件。

数据库提交与文件移动无法组成一个跨系统原子事务，因此必须允许并展示“文本已保存，原件未就绪”“原件存在但记录未完成”等内部恢复状态。用户界面只显示可理解的结果，不暴露路径和堆栈。

原件打开/下载必须先校验当前人物和对象归属，再通过存储键读取，不能使用用户提供的原始文件名直接拼接路径。

## 7. 接口契约

### 7.1 通用规则

- API 前缀为 `/api/v1`，JSON 使用明确字段名和稳定错误结构。
- 需要写入的 POST/PUT/PATCH 请求使用 `Idempotency-Key`；同键相同请求返回原状态，同键不同请求返回 `IDEMPOTENCY_KEY_REUSED`。
- DELETE 参考关系操作同样携带幂等键与预期范围版本；过期页面的删除不得静默覆盖另一页刚建立的关系。幂等重放返回操作结果，异步执行进展另查请求接口；键到期清理后不能自动把未知旧操作重新当作新模型调用。
- 更新请求携带 `expected_version` 或等价版本条件；不匹配返回 `VERSION_CONFLICT`，不覆盖服务端内容。
- 所有资源先做登录、人物归属、工作区归属和权限校验；不存在或无权访问不泄露其他人物信息。
- 普通创建成功返回 201，异步受理返回 202 并给出状态查询地址；查询/更新成功返回 200 或无正文的 204。参数错误 400、未登录 401、CSRF/权限拒绝 403、不可见对象 404、版本/重复键/同区请求冲突 409、资料容量超限 422、受理限流 429、依赖暂不可用 503。查询成功但任务失败仍是 200，由任务状态表达，避免误导客户端重新提交。
- 错误响应包含稳定 `code`、用户可用 `message`、是否可重试的 `retryable` 和必要的 `request_id`，不包含 SQL、堆栈、文件路径、密钥或完整供应商原文。

### 7.2 主要资源接口（目标契约）

| 方法 | 路径 | 作用 | 关键规则 |
| --- | --- | --- | --- |
| `GET` | `/profiles` | 列出人物档案 | 只返回当前操作者可见对象 |
| `POST` | `/profiles` | 创建人物档案 | 幂等；名称校验；同名只提示不合并 |
| `GET/POST` | `/profiles/{p}/workspaces` | 列出/创建工作区 | 校验人物归属；同名可创建 |
| `GET` | `/profiles/{p}/workspaces/{w}` | 获取工作区和状态 | 返回待建立、最近编辑和范围摘要 |
| `POST` | `/profiles/{p}/workspaces/{w}/resume/initialize` | 导入或复制建立简历 | 目标仍未初始化时才允许；独立生成 |
| `GET` | `/profiles/{p}/workspaces/{w}/resume` | 获取当前简历 | 返回文本、版本和来源信息 |
| `PUT` | `/profiles/{p}/workspaces/{w}/resume` | 保存简历 | 版本条件更新；冲突不覆盖 |
| `GET/POST` | `/profiles/{p}/materials` | 列出/添加材料 | 解析失败不进入可参考范围；文件和文本状态分别反馈 |
| `PATCH` | `/profiles/{p}/materials/{m}` | 重命名或编辑材料 | 版本条件更新；不自动调用 AI |
| `PUT/DELETE` | `/profiles/{p}/workspaces/{w}/references/{m}` | 建立/停止参考关系 | 只允许同人物；不触发模型调用 |
| `GET` | `/profiles/{p}/backgrounds` | 查看有效背景 | 只返回已确认且未撤回记录 |
| `POST` | `/profiles/{p}/background-candidates` | 创建或获取待确认候选 | 候选不是有效背景 |
| `POST` | `/profiles/{p}/background-candidates/{c}/confirm` | 确认候选 | 绑定候选版本和明确确认内容，幂等保存 |
| `POST` | `/profiles/{p}/backgrounds/{b}/correct` | 提交纠正候选 | 不直接覆盖，先形成新候选 |
| `POST` | `/profiles/{p}/backgrounds/{b}/withdraw` | 撤回背景 | 状态更新；不删旧消息 |
| `GET/PUT` | `/profiles/{p}/workspaces/{w}/draft` | 获取/保存输入草稿 | 一份草稿；失败不阻塞发送，版本冲突不静默覆盖 |
| `GET/POST` | `/profiles/{p}/workspaces/{w}/conversation` | 获取对话/受理消息 | 受理时固定资料和上下文；同区一次一条 |
| `GET` | `/profiles/{p}/workspaces/{w}/requests/{r}` | 查询 AI 请求 | 返回状态、回答、保存状态和依据摘要 |
| `POST` | `/profiles/{p}/workspaces/{w}/context-boundaries` | 创建上下文分隔点 | 保留旧消息但后续不携带旧聊天 |
| `POST` | `/profiles/{p}/workspaces/{w}/conversation/clear` | 清空记录并开始新对话 | 同时清空消息和草稿；回答期间拒绝 |

具体请求/响应 DTO、分页字段和数据库列名在实现前以测试先行的接口样例收口；不直接把现有旧接口当作新方案的完整契约。

异步提交的最小形态为：请求体含 `message`、`expected_conversation_version`、`expected_context_epoch`、`expected_scope_version`、`reference_resume` 及资料预期版本，幂等键放请求头；响应含 `request_id`、`user_message_id`、`execution_status`、`record_status` 和 `status_url`。资料真实文本和归属由后端获取，不能使用浏览器提供的任意正文作为已保存依据。

查询请求返回 `request_id`、上述两类状态、可用 `answer`、安全错误码、依据版本和 `used_history_boundary`。回答保存重试使用 `POST /profiles/{p}/workspaces/{w}/requests/{r}/persist`，只重试已有结果；模型手动重试则使用新操作键，引用原请求，不能复制原用户消息。导入预览、原件下载和资料范围设置另设受保护子资源，必须遵循相同归属、大小和版本约束。

聊天或范围在别页变化时，发送前的版本条件必须在受理事务内再次校验，不能仅靠前端提前查询；清空/分隔操作也要求预期对话版本及无活动请求。分隔会递增上下文代次，清空同时改变代次并清除草稿；后续调用不得关联供应商旧会话。

### 7.3 错误与恢复语义

| 错误码 | 含义 | 客户端行为 |
| --- | --- | --- |
| `AUTH_REQUIRED` | 登录已失效 | 保留输入，原页重新登录，不自动重放 |
| `VALIDATION_ERROR` | 输入不符合要求 | 就近提示并修改后重试 |
| `OWNERSHIP_DENIED` | 对象不属于当前人物/工作区 | 不继续尝试其他对象，显示无权访问 |
| `VERSION_CONFLICT` | 服务端已有更新 | 保留本地输入，展示最新内容供核对 |
| `IDEMPOTENCY_KEY_REUSED` | 同键对应内容变化 | 生成新操作键，不能覆盖原操作 |
| `REQUEST_IN_PROGRESS` | 同区已有未结束请求 | 查询原请求，不创建第二次模型调用 |
| `CAPACITY_EXCEEDED` | 必需资料无法完整放入 | 调整范围或内容后重新发起 |
| `MODEL_RESULT_UNKNOWN` | 外部调用结果不明 | 不自动重调，等待查询或人工决定 |
| `PERSISTENCE_FAILED` | 本系统保存失败 | 保留可见内容，按对象提供重试/复制，不重做外部调用 |
| `FILE_NOT_READY` | 原件未就绪或不可用 | 可继续使用可读文本，提示原件问题 |

## 8. 安全、日志与数据生命周期

### 8.1 安全边界

- 模型密钥、数据库口令不进入前端或数据库快照；Session Cookie 由浏览器按会话机制持有，设置 HttpOnly，不向前端脚本提供其值。上述凭据均不进普通日志或错误响应。
- 所有对象访问执行服务端归属检查；文件下载不信任文件名和客户端路径。
- 保留 HttpOnly、SameSite、Secure（在 HTTPS 部署时）Cookie、CSRF、登录限流和安全响应头。
- 材料、背景和聊天不能自动扩大模型使用范围；用户选择并主动发送才调用，实际范围由后端组装。
- 模型输出不拥有写入背景、简历或材料的权限；确认保存是独立的业务操作。

### 8.2 日志和执行快照

默认日志只记录请求编号、对象类型、状态、耗时、错误类别、供应商请求标识和可安全记录的用量信息，不记录简历、材料、背景、聊天正文、完整提示词或回答。供应商错误先过滤，不能把输入原文带回日志。

执行快照用于已受理请求的必要执行和恢复，与长期聊天记录分开管理；不含密钥，限制访问并设置清理周期。MVP 不提供默认记录全部提示词的调试开关，问题研究优先使用人工构造的无隐私数据。

### 8.3 生命周期

临时上传文件、孤儿文件、已完成请求快照、幂等结果和失败记录的具体清理期限由部署和测试确定。清理不能删除用户仍可回看的对话、有效背景或工作区简历；任何删除策略都要先区分“业务数据”“恢复数据”和“排错元数据”。

## 9. 验证计划与已知边界

### 9.1 最小验证集

- 两个标签页同时保存简历：一个成功，一个收到版本冲突，不能覆盖。
- 同一幂等键重复提交：返回同一受理结果；改 payload 则拒绝。
- 同区同时发送：只产生一个 AI 请求。
- 请求受理后离开页面、刷新和重新登录：查询原请求，不重复调用。
- 模型已返回但对话保存失败：回答仍可见，重试只保存，不新增模型调用。
- 材料文本已保存但原件失败：分别显示状态，文本仍按规则可用。
- 不同人物使用相同材料编号：服务端拒绝，数据库约束不允许跨人物关联。
- 背景候选被修改或撤回后使用旧确认：拒绝过期写入。
- 日志和错误响应扫描：不出现正文、密钥、Cookie、SQL 和本地路径。

### 9.2 当前不能承诺的能力

- 不承诺供应商调用端到端恰好一次、一定支持查询、取消或费用查询。
- 不承诺应用进程在“模型已返回但数据库尚未保存”窗口崩溃后一定恢复回答正文。
- 不做实时多页面协同、自动合并编辑、自动聊天摘要或完整模型请求日志。
- 本地文件目录不是高可用对象存储；备份和迁移必须同时覆盖数据库与原件目录。

## 10. 待开发验证与重新评估条件

### 10.1 以阶段设计为准的实现与旧资源隔离

当前仓库已有档案、工作区、材料、简历版本、参考关联、幂等记录和回收相关实现；但材料确认门禁、从材料初始化和替换接口等历史逻辑不等于新产品规则。对话、后台模型任务、候选确认和有效背景属于待新增能力。

本轮按 01—04 的目标设计实现，可以重构或重写不合适的旧模块，不以补齐旧系统或兼容旧表结构为默认路线。目标工程使用隔离数据库/schema 与文件目录，建立自己的 Flyway 初始化及后续增量链路；不修改旧环境已应用的 V1—V4，也不删除旧数据、文件或已有工作树变更。

目标入口不暴露与新设计冲突的旧业务路径，旧测试不作为需求来源，旧回收能力不成为本轮新增 MVP 需求。旧代码只有满足目标契约并经本轮验证后才计入复用结果，不能以保留旧行为改变设计。

旧数据迁入不是默认 MVP 完成条件。确需迁入时另列任务，先备份并在副本演练映射与恢复；旧人工修订不能丢失，旧“材料确认”不能转换为背景确认。不因允许按新设计重写而默认为可清空旧库，本文也不宣称旧数据已经兼容。
