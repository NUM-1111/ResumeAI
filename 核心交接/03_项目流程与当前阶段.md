## 已确认的业务基线

- 个人档案对应一个人，保存跨岗位工作区复用的背景；不同人的背景与文件隔离。
- 支持删除个人档案；删除前展示影响并要求确认，确认后进入可恢复回收站，不影响其他档案。恢复期限与清理边界留待设计明确。
- 支持单独删除工作区；删除前展示该区简历、JD、材料、历史稿、分析等影响并要求确认，确认后进入可恢复回收站，不影响个人档案及其他工作区。恢复期限与清理边界留待设计明确。
- 一个工作区维护一份可独立持续修改的目标简历及相关JD、引用材料、分析和修改记录；方向是属性，同方向可建立多个工作区。更换目标时由用户选择继续当前工作区或新建。
- 加入或切换JD时，由用户决定从已有简历另建工作区，还是继续修改当前稿。默认明确选择单份JD分析，也允许明确选择多份综合分析并区分来源与侧重点；不默认糅合不同目标。
- 工作区内保留线性修改历史，可查看并恢复历史稿；恢复为新当前稿并保留恢复前稿件。并行维护另一目标简历用新工作区，不建立复杂版本分支。从来源工作区当前简历另建时，辅助材料由用户选择沿用；来源JD、分析和未采用建议默认不带入，同一档案的已确认背景继续复用。切换分析目标后可提示重新分析，但不自动运行；旧建议保留查看、标明原目标并暂停采用，须按新目标重新处理后再授权写回。
- 首次使用先建个人档案和工作区，再定岗位方向、导入并检查确认简历；再次使用可继续已有工作区。
- 档案文件区首轮支持简历、项目说明、面试记录等基础材料。提取文本检查确认并明确引用后才进入工作区上下文。允许单独移除材料；已引用时展示关联和影响并确认后解除引用，当前简历材料须先更换后才能移除。
- 每个工作区有一份当前简历。新建工作区可使用已有工作区的当前简历或直接导入新简历；现有工作区导入新稿经检查确认后，可更新当前稿、另建一份或仅保存为材料。更新时比较后整体替换或逐项采纳，旧稿保留为历史；另建不覆盖原区；仅存材料不自动参与分析。
- 整份替换只选择当前简历文件，不确认其中全部事实；新增/冲突事实仍待确认，用户明确确认后才同步个人档案。
- 清楚的自然语言事实陈述可作为明确确认；同步结果须展示并允许纠正或撤回。含糊、假设或冲突内容先追问，不静默覆盖已确认背景；采用措辞不等于确认事实。
- 纠正或撤回背景不自动修改已保存简历，对已识别的相关内容提示核查；依赖旧事实的待采用建议暂停直接采用，按新背景重新处理。撤回不等于判假，不承诺识别所有语义关联，依赖识别机制留到设计阶段明确。
- 模型可以调度分析、追问和建议，但不能认证事实或自行写回；程序保护档案、材料引用、版本、授权和错误状态；用户负责确认事实与决定是否采用。
- 采用授权支持页面操作和对象、范围明确的自然语言，两者执行相同校验；请求改写不等于授权写回，指向不明先澄清，只改用户授权范围。
- 用户可查看并恢复工作区历史稿；恢复时作为新的当前稿，保留恢复前稿件，不回退个人档案事实，也不重新激活旧建议。
- 失败必须显式提示。保存失败显示未保存，尽量保留页面内容并给文本兜底，不承诺关闭后恢复；导出失败不能显示成功，已保存稿件应保留。
- 当前内容未保存时切换档案或工作区，不得静默切换；提示未保存，允许重试或复制文本后明确离开。
- 新建工作区可复制同档案已有工作区当前稿、选择已检查确认的档案简历材料、或导入新稿，均形成独立可编辑当前稿，禁止跨人选取。
- 材料撤销引用、移除或更新后，依赖该材料或旧内容的未采用建议暂停；已保存简历不自动修改，历史任务摘要标示依据变化。
- 导出遇到未保存内容时须明确状态，可复制/下载页面当前文本，不静默输出旧稿；导出成功不等于工作区保存成功。
- R11要求重新打开工作区可回看AI关键判断、简要依据/未知及用户处理结果；不改稿的分析/追问也可留摘要，记录失败不得显示为已保存。

### 可以考虑择优复用的机制

| 机制 | 现有证据 | 边界 |
| --- | --- | --- |
| Java 17、Spring Boot、LangChain4j 模型调用 | `pom.xml`、`ResumeScoringAgent`、`ResumeWriterAgent` | 作为候选技术经验；不代表新项目必须使用 |
| JD评分/技术缺口建议 | `ResumeDecisionService`、`ResumePlanningAgent`、`SupplementItem` | 只覆盖现有词典技术判定，不等于完整岗位能力分析 |
| 纯文本分段 | `ResumeParser` | 正则分段，不支持PDF/Word文件解析，存在错切风险 |
| Critic与事实工具 | `FactCriticAgent`、`FactCheckTool` | 工具比对模型传入片段，不提供真实经历认证或可靠来源绑定 |
| JSON容错、SSE和异常处理 | `JsonSanitizer`、`StreamEvent`、`GlobalExceptionHandler` | 可参考实现，须按新状态和失败规则重验 |
| 当前静态前端 | `src/main/resources/static/index.html` | 只有文本输入、结果展示、复制和Markdown下载，无档案/工作区持久化与受控写回 |

### 旧主流程不能直接承载的新需求

- 请求对象只有JD和简历文本，没有档案、工作区、当前版本、文件引用或用户确认状态。
- 旧服务是固定评分→缺口决策→Writer→Critic管线，不是新产品的持续档案和自然对话任务流程。
- 旧管线审查不通过时可能仍返回最后草稿；新产品要求建议、用户采用和正式简历分离。
- 旧输出缺少稳定句子位置、来源ID、简历版本绑定和用户授权，无法直接实现受控局部写回。
- 当前依赖中未见持久化和文件解析组件；这只是当前检查结果，不证明从未有过其他实现。

**勘查结论：**按需求重建新产品主体；旧模块仅在新需求需要且代码/测试验证适配后才复用，不因“能搬”而搬。

## 实施方式建议（由用户决定）

采用分阶段、每阶段可运行可验收的垂直切片，不一次生成完整系统。建议顺序：

1. 新项目骨架和运行说明。
2. 档案/工作区/当前简历的文本导入、保存、编辑和重新打开。
3. 用户补充事实→模型生成带依据建议→对照→采用/拒绝→程序校验版本并写回。
4. JD分析、主动疑点、缺口建议和辅助材料引用。
5. 新简历比较、版本保留、PDF/Word处理及文本兜底。
6. 用真实简历/JD做首轮端到端验收。

### 运行环境与Java/Spring技术栈参考

以下是官方资料和本机检查结果，用于比较选项，不代表已经选定技术栈。

#### WSL还是Windows

Microsoft官方WSL文件系统指南（页面标注最后更新2022-03-03）建议：使用Linux命令行时把项目放WSL的Linux文件系统以获得最快文件访问；使用Windows命令行/工具时把项目放Windows文件系统。跨文件系统访问可用，但可能较慢，也会遇到大小写等行为差异。指南也说明可通过`\\wsl$`/资源管理器访问Linux文件。

结合本机情况：旧仓库位于WSL Linux文件系统，WSL发行版可用；本机WSL报告Java 17.0.15、Maven 3.6.3。但用户担忧环境偶发错误和调试成本。建议决策标准不是单看构建速度，而是选择一个主工作树与匹配的工具链，避免同一项目在Windows/WSL两处双向编辑。

来源：[Microsoft WSL文件系统指南](https://learn.microsoft.com/en-us/windows/wsl/filesystems)。

#### 我的建议（已部分采纳，不等于所有技术细节已锁定）

1. **候选起步组合：Java 17 + Spring Boot 3.5.x + 匹配版本的LangChain4j。** 理由是本机已有Java 17.0.15/Maven 3.6.3，旧项目有经验，变量较少；需要用最小原型验证，不代表它在技术上绝对优于Java 21/Boot 4。
2. Java 21 + Boot 3.5.x作为对照候选；Boot 4.1作为更高变化量候选，需验证专用starter和依赖兼容。
3. 不默认沿用LangChain4j 0.36.2；以选定JDK、Boot和starter的最小启动验证结果固定版本。
4. 选择标准：本地稳定运行/调试 > 依赖兼容和官方支持范围 > 个人熟悉度/面试可解释性 > 新版本新颖度。
