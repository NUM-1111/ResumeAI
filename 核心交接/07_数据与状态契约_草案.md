# AgentCV 数据与状态契约（详细设计草案）

> 依据：已确认的R01—R11、B01—B03及12文档已接受机制。数据层采用Spring JDBC，迁移采用Flyway；逻辑字段/约束为评审稿，精确依赖版本待验证。不创建工程或执行DDL。

## 1. 设计原则与类型约定

- PostgreSQL保存业务数据，本地受控目录保存原文件。确认文本和简历工作稿不能只保存在浏览器内存。
- 对象ID建议使用UUID；业务修订号使用递增整数；时间使用带时区时间戳并统一按UTC存储。最终长度和索引通过数据规模与查询评审确定。
- 所有工作区子对象保留`profile_id`、`workspace_id`归属；服务端从有效对象链核对，不信任页面传入的归属声明。外键和同档案组合约束作为数据库防线。
- 内容历史不可原地覆盖；生命周期、业务修订、确认状态、保存状态分别表达，不混成一个`status`。
- 下表是逻辑数据字典；正式建表仍需补齐字段必填性、外键删除策略、索引、迁移顺序和数据保留范围。

## 2. 核心数据字典

| 对象 | 关键字段建议 | 约束与用途 |
| --- | --- | --- |
| Profile | id、display_name、background_version、row_version、lifecycle | 档案根；事实变更推进background_version，用于分析上下文校验 |
| Workspace | id、profile_id、name、direction、target_version、row_version、lifecycle | 一区一份独立目标简历；改变分析目标推进target_version |
| Material | id、profile_id、original_name、kind、latest_revision_id、row_version、lifecycle | 材料身份稳定，文件名不作为唯一键；kind区分简历/项目说明/面试记录等 |
| MaterialRevision | id、material_id、revision_no、storage_key、hash、byte_size、format、extracted_text、confirmed_text、parse_state、check_state、confirmed_at | 同材料修订号唯一；旧修订不覆盖；新修订不能继承旧确认；原文件和确认文本分别保存 |
| WorkspaceMaterial | id、profile_id、workspace_id、material_id、revision_id、reference_state、row_version | 同工作区同材料至多一个有效引用；修订必须归属该材料及档案；引用身份用于失效检查 |
| JobDescription | id、profile_id、workspace_id、title、revision_no、text、source_material_revision_id、lifecycle | 粘贴或导入；更新生成可区分修订，不用修改后的文本解释旧分析 |
| AnalysisTarget | workspace_id、mode、selected_jd_revisions、direction_snapshot、version | mode为SINGLE_JD/MULTI_JD/DIRECTION；JD集合与mode一致；集合次序不是目标变化依据 |
| CurrentResume | workspace_id、profile_id、revision_no、text、content_hash、source_kind、source_id、source_revision_id、row_version | workspace_id唯一；初建未选稿可没有记录；来源为区当前稿/材料修订/历史恢复等，工作文本独立 |
| ResumeRevision | id、workspace_id、profile_id、revision_no、text、reason、source_revision_id、created_at | 工作区修订号唯一；只追加。reason区分初始化、编辑保存、采用、替换、恢复 |
| ResumeProvenance | resume_revision_id、source_type、source_id、source_revision_id | 不可变历史出处；不授予分析读取权限，不因来源不可用而删除稿件文本 |
| ResumeSourceBinding | workspace_id、material_id、profile_id、row_version | 当前来源绑定；同档案材料集合独立于辅助引用；复制区时继承，独立文本稿操作可明确解除 |
| 当前来源集合版本 | CurrentResume.source_version | 初始化、替换、复制、逐项采纳、恢复或独立化导致绑定集合变化时递增；与expectedSourceVersion校验，不能只核对单条绑定版本 |
| ProfileFact | id、profile_id、current_revision_id、row_version | 事实稳定身份；不代表现实认证 |
| FactRevision | id、fact_id、revision_no、text、state、user_statement、source_type、source_id、created_at | 状态区分SELF_REPORTED/USER_CONFIRMED/PENDING/CONFLICT/WITHDRAWN；保留清楚陈述来源及纠正历史 |
| TaskRecord | id、profile_id、workspace_id、goal、created_at、summary_state | 用户任务容器，不以改稿为创建前提；允许包含多个分析/追问回合 |
| TaskSummary | id、task_id、sequence、public_judgment、brief_reasons、unknowns、input_identity、created_at | 按回合追加，不改写旧判断；不是隐藏思维链；输入身份与实际运行记录关联 |
| AnalysisRun | id、task_id、input_snapshot、run_state、freshness、failure_code、started_at、finished_at | input_snapshot含简历修订、背景版本、目标版本、所选JD修订和有效材料引用/修订；模型调用在事务外 |
| Suggestion | id、run_id、workspace_id、base_resume_revision、patch_items、decision_state、eligibility、invalid_reasons、row_version | 建议内容与目标范围固定；调整生成新建议，原建议保留；用户决定与可采用性分开 |
| SuggestionSource | suggestion_id、source_type、source_id、source_revision、reference_id | 程序校验引用存在且属于本次输入；不能借合法来源ID证明语义正确 |
| TaskAction | id、task_id、operation_id、action_type、suggestion_id、authorized_scope、result、result_revision、created_at | 由程序记录用户决定与真实结果；成功写回结果与稿件同事务提交 |
| Operation | id、profile_id、workspace_id、request_key、request_hash、state、result_reference | 幂等请求；同key不同payload拒绝；同请求重试返回既有结果，不再次写回 |
| RecycleEntry | id、profile_id、object_type、object_id、delete_batch_id、deleted_at、expires_at、state | 区分本次级联和此前已删除对象；不能恢复父对象时误复活此前独立删除的内容 |

嵌套快照、patch与原因列表可评估JSONB，所有权、唯一约束、版本及主查询字段使用明确列。不因采用JSONB省略结构校验。

## 3. 状态机与转换

### 3.1 材料：解析、检查、引用三轴分离

- `parse_state`：QUEUED → PARSING → EXTRACTED / PARTIAL / FAILED；不支持或超限在校验阶段直接拒绝。
- `check_state`：PENDING → CONFIRMED；用户修改提取文本并确认后保存新确认文本。材料再次更新产生新修订并回到PENDING。
- `reference_state`：ACTIVE / REVOKED / NEEDS_RECONFIRMATION。可分析条件为材料及父档案有效、引用ACTIVE、引用修订已确认，且不存在尚未确认的材料更新。
- 撤销/移除不自动删除历史依据身份。材料更新后旧引用不得继续向新分析提供旧文本；重新检查确认并确定有效引用后才可使用。
- 检查确认和引用可以是一次用户操作，但数据库分别保存两项状态，事务失败时不得只完成一半。

### 3.2 建议：用户决定与可用性分离

- `decision_state`：PENDING → ACCEPTED / REJECTED / SUPERSEDED。
- `eligibility`：VALID / PAUSED / STALE；原因可包含TARGET_CHANGED、RESUME_CHANGED、FACT_CHANGED、MATERIAL_CHANGED、REFERENCE_REVOKED、PARENT_RECYCLED。
- ACCEPTED仅表示授权变更已成功提交；用户表达采用但数据库失败，建议不能标为ACCEPTED，页面显示失败/未保存。
- 目标、原文、已知依据变化使旧建议不可直接采用；重新处理产生新建议，不靠把旧建议状态改回VALID绕过新确认。
- 暂停建议保留查看；切回旧JD也不自动激活。来源语义关系仍有漏识别风险，不承诺检测所有语义关联。

### 3.3 分析、记录与页面保存

- `run_state`：QUEUED → RUNNING → WAITING_USER / SUCCEEDED / FAILED / CANCELLED；重启遗留QUEUED/RUNNING置INTERRUPTED；`freshness`独立为CURRENT/STALE。WAITING_USER结束本回合，补充创建新run；运行成功不表示结果仍适用于当前稿。
- 追问是正常任务结果，不伪装为失败；格式错误、超时、缺关键结构等失败结果不生成可采用建议。
- `summary_state`：PENDING / SAVED / FAILED；摘要失败与简历事务成功互不冒充。
- 页面保存：CLEAN → DIRTY → SAVING → CLEAN / SAVE_FAILED / CONFLICT。CLEAN只能对应服务端确认的页面内容，不能由下载成功触发。
- 保存请求携带页面编辑序号；响应只确认该序号。等待响应时产生的新编辑仍为DIRTY，防止旧响应将新内容标为已保存。

## 4. 事务边界及并发控制

### 4.1 采用建议

1. 页面存在未保存编辑时，先明确保存或处理冲突；不以服务端旧稿接受建议覆盖页面新编辑。
2. 请求携带operation key、建议ID、预期简历修订、建议版本与明确范围；自然语言授权先唯一定位对象，歧义先澄清。
3. 短事务内校验对象归属及生命周期，并按统一锁顺序锁定/校验工作区、依赖、当前稿与建议。所有改变相同上下文的命令遵循相同并发协议，避免“校验后引用被撤销仍写回”。
4. 校验目标版本、简历修订、事实依赖、材料修订及引用状态；用基础文本的明确范围和原文匹配验证patch。找不到或多处匹配不能猜位置。
5. 原子更新当前稿、追加ResumeRevision、更新建议决定、记录TaskAction与Operation成功结果；任一失败全部回滚。模型调用不在此事务中。
6. 文字摘要可另行保存，失败仅重试摘要。响应丢失时以operation key查询结果，不让用户重复采用造成二次变更。

已确认：同一次多个修改项一起采用时，在同一新修订中原子应用，全部成功或全部失败；若只采用部分，剩余项基于旧稿暂停，重新处理后再采用。不能直接按旧偏移继续写入。

### 4.2 自动保存、替换与恢复

- 保存采用预期修订的条件更新；同一工作区多标签页冲突返回冲突结果，不采用最后写入覆盖。
- 已确认：内容变化的成功保存保留修订，当前稿与对应历史同事务持久化；历史界面简短组织并突出关键操作，不把每次按键作为用户可见版本。具体保存频率、编辑合并及历史展示方式待验证。
- 整体替换/逐项采纳按同样版本校验执行；事实同步是独立明确行为，不能由替换自动触发。
- 恢复旧稿用其文本创建新修订，不移动版本指针回旧号，不回滚事实、不激活旧建议。保存失败保留页面候选内容并显示未保存。

### 4.3 分析快照及上下文变化

- 用户发起时构造可识别且自洽的输入快照，只包含当前档案下有效引用、明确选择JD和实际发送内容。
- 已确认：分析前自动保存待分析的页面编辑；保存失败时提示重试或文本兜底，不发起分析，不静默使用服务端旧稿。无需用户为每次分析额外执行手动保存。
- 模型在事务外执行；返回后及采用前再检查输入身份。运行期间改变上下文的结果标STALE并保留历史，不直接采用。
- 已知依据状态检查和上下文版本检查在程序中实现；模型输出来源只能引用本次输入白名单，不能引用任意文件或跨人ID。

## 5. 文件与数据库一致性

1. 上传写入受控临时目录，按文件签名、声明格式、容量检查；随机storage key，不能以用户文件名拼接目录。
2. 完成文件写入后，将原件放入正式受控位置，再提交MaterialRevision元数据；只有提交成功的对象才可进入后续提取/确认流程。
3. 文件存在而数据库提交失败属于孤立文件，进入补偿清理；数据库存在而文件丢失标明不可用，不能继续伪装可读取。补偿应有状态和可重试记录。
4. 解析器读取本地文件，不将文件内指令视为工具授权；使用时间/内存/解压等限制候选，具体参数须用异常样本确定。
5. 回收站先逻辑删除，首轮不自动永久清理；人工维护清理前明确影响并备份。备份恢复采用10文档已确认策略，必须包含数据库及其引用文件的一致集合，只有数据库备份不构成完整恢复。

## 6. 删除、恢复和关联边界

- 删除工作区只回收该区简历、历史、JD关联、任务记录、建议及引用，不回收档案拥有的共享材料和事实。
- 档案删除形成delete_batch；此前独立回收的对象不因恢复档案自动复活。材料恢复不静默恢复引用。
- 恢复工作区要求所属档案有效；不满足时提示先恢复父档案。对象ID不复用；同名显示冲突不允许覆盖其他对象。
- 材料仍被任何有效工作区选作当前简历来源时阻止直接移除，显示这些工作区；先明确更换当前稿。普通文本编辑不自动解除该来源关联。
- 已确认：复制来源区当前稿得到独立文本和历史出处，同时复制有效当前来源材料绑定；原区后续修改/删除不改新区文本。逐项采纳新材料将其加入当前来源集合，不自动创建辅助引用。
- 更换简历或明确“转为独立文本稿”在事务中创建新修订并更新当前来源集合，保留历史出处；后者清空材料绑定，不撤销辅助引用/个人事实。普通编辑不自动解除绑定。
- 历史恢复始终可恢复保存的文本；仅仍有效的材料恢复当前绑定，无效材料提示不可用，不自动复活材料、引用或旧建议。

## 7. 接口公共契约建议（非完整API清单）

| 操作 | 必须携带/检查 | 成功返回 | 冲突或失败 |
| --- | --- | --- | --- |
| 保存当前稿 | workspaceId、expectedRevision、text、clientEditSequence、requestKey | 新修订及已保存编辑序号 | 版本冲突不覆盖，保留页面内容 |
| 采用建议 | suggestionId、expectedRevision、明确scope、requestKey | 实际写回修订及操作结果 | 依据失效/歧义/版本冲突不写回 |
| 更新并确认材料 | materialId、expectedRevision、确认文本 | 新修订/确认状态 | 旧版本提交不覆盖新内容 |
| 更改引用/目标 | 对象归属、expectedVersion、明确引用或目标集合 | 新上下文版本、依赖状态 | 不触发自动分析 |
| 发起任务 | workspaceId、简历修订、明确目标和用户请求 | taskId/runId及初始状态 | 输入不完整或失效须提示 |
| 回看任务 | taskId及归属 | 原目标、摘要、未知、操作结果和变化标记 | 文件已清理时不伪造原件仍可查看 |
| 删除/恢复 | 对象ID、影响预览版本、确认、requestKey | 实际生命周期结果 | 影响变化先重新预览，不静默误删 |

HTTP候选：400输入错误、401/403访问保护失败、404归属范围内不存在、409版本/依据冲突、413超限、422格式或业务不可处理、503模型/存储暂不可用。具体状态码及错误结构须在完整接口设计评审，不能仅凭表格视为已完成OpenAPI。

统一错误建议包含`code`、可读`message`、`requestId`、实际结果/操作查询标识和可行下一步；不向页面泄露密钥、服务器路径或堆栈。

## 8. 设计验证案例与未决项

| 检查案例 | 预期 |
| --- | --- |
| A页面建议生成后，B标签页保存新稿 | A采用返回版本冲突，不覆盖B |
| 采用请求成功但响应丢失，用户重试 | 同operation key返回原结果，不新增第二次修订 |
| 模型运行时材料更新或撤销引用 | 返回结果标过期；不可采用；新分析不得使用旧输入 |
| 简历保存成功但摘要失败 | 简历显示已保存，摘要显示记录未保存；只重试摘要 |
| 未保存页面导出成功 | 文本是页面快照，保存状态仍未保存 |
| 删除工作区但材料被其他区引用 | 其他区及档案材料不受影响 |
| 文件已写入但元数据提交失败 | 不显示导入成功，孤立文件可补偿清理 |

分析前自动保存、批量采用原子性、修订保留及来源绑定机制已确认。后台有界执行、状态轮询及重启不自动重放按12文档执行；待验证保存频率/历史展示、锁与条件更新、组件版本、索引、文件补偿/备份、解析限额和模型协议。本文未执行数据库或模型验证，不据设计案例宣称测试通过。
